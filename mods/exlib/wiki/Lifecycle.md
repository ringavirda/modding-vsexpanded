# Lifecycle

Where exlib's own `ModSystem`s sit in the game's mod-loading sequence, what each has done by the
time it hands control to your mod, and what you may safely call at each point. Phases are the
vanilla `ModSystem` hooks (`StartPre`, `Start`, `AssetsLoaded`, `AssetsFinalize`,
`StartServerSide`/`StartClientSide`, `Dispose`); the game calls every mod's method for one phase, in
`ExecuteOrder` order, before moving to the next phase. exlib is a runtime dependency, so its
`ModSystem`s exist (are constructed) before your mod's `Start` runs, and - because a dependency's
mods load first - its calls for each phase run before yours at the same `ExecuteOrder`.

| Phase | What exlib has done by then | What you may call here |
| --- | --- | --- |
| `StartPre` (`ExecuteOrder` 0.0) | `ExModsModSystem.StartPre` sets `ExMods.FlagKey(modId)` to `true` in `api.World.Config` for every enabled mod, on both sides from each side's own local mod list, well ahead of the JSON patch loader's `AssetsLoaded` at 0.05. | Too early for anything else below; blocks/items/recipes are not registered and no assets are read yet. |
| `Start` (default `ExecuteOrder` 0.1) | `ExModsModSystem.Start` sets the same flags again (idempotent; a defence in case `World.Config` was not yet available at `StartPre`). `ExpandedLibModSystem.Start` has loaded `ExlibValues`, registered exlib's own `[BlockRegister]`/`[BlockEntityRegister]`/`[BlockBehaviorRegister]` classes (the structure filler, the multiblock-structure behaviour) via `EntityRegistry.RegisterAll`, and pointed `StructureFillers.FillerCode` at the shared filler block. `BlockNetworkModSystem` and `BlockMigrationModSystem`/`BlockEntityHealModSystem` exist as separate auto-loaded `ModSystem`s but have not yet run their own `StartServerSide`. | Your config load (`*Values.Load(api)`); `EntityRegistry.RegisterAll(api, Mod, GetType().Assembly)` (registers your classes and discovers your `IExBlockDefProvider`/`IExItemDefProvider`/`IExRecipeDefProvider` types into `ExDefinitions`); `ExRecipeProfiles.Register(...)`; `ExRccSettings.RegisterBrokenDropsRatio(...)`; `api.ModLoader.GetModSystem<BlockNetworkModSystem>().RegisterNetworkType(...)`; `ExHarmony.PatchOnce(Mod, GetType().Assembly)`. Deriving `ExModSystem` runs the config load, `EntityRegistry.RegisterAll` and (if `PatchHarmony` is set) `ExHarmony.PatchOnce` here for you, then calls your `OnStart`. |
| `AssetsLoaded` 0.04 | `ExDefinitionModSystem.AssetsLoaded` (server-only: `ShouldLoad` returns `side == EnumAppSide.Server`) reads everything registered into `ExDefinitions` during every mod's `Start` and injects it as synthetic `blocktypes/`/`itemtypes/`/`recipes/{category}/` assets - including the metal-family items (`MetalFamilyEmitter`) and the process-route stopping-point items (`ProcessItemEmitter`), both read straight off the `config/` catalogues since the registries that would normally serve them are still empty at this phase. | Nothing - this phase is exlib's own injection step. Anything you need it to see must already be registered by the time your `Start` returned (see Ordering rules below). |
| `AssetsLoaded` 0.05 | The game's own JSON-patch loader runs (vendor default `ExecuteOrder`, not an exlib phase). Patches can now target the assets exlib injected at 0.04, the same as any file asset. | Nothing exlib-specific. Blocks/items are still unregistered below `ExecuteOrder` 0.2; recipes below 0.6. |
| `AssetsFinalize` | `ExpandedLibModSystem.AssetsFinalize` first runs every [content check](Checks) (`Checks.ExlibChecks.All`) over the live game state and logs the results, unless `ExlibConfig.RunChecksOnLoad` is off - also available on demand with `/exmod verify`. It then clears and reloads the metal catalogue (`MetalCatalogueLoader.Load`), the fluids catalogue (`ExLiquids.Load`), the material-role catalogue (`MaterialRoleLoader.Load`), the process-route catalogue (`Processes.ProcessRouteLoader.Load`), the process-job catalogue (`Processes.ProcessJobLoader.Load`), and the storage bay-occupancy catalogue (`Storage.BayOccupancyLoader.Load`) - all post-JSON-patch, so every mod's merged config is what these registries hold from here on. Each `Load` runs its catalogue's code contributors (`Registries.CatalogueContributors`, one per registry) after its JSON read, then returns a `Registries.CatalogueLoadReport` that `AssetsFinalize` logs: files read, entries accepted, and one `Error` per malformed asset or clash naming its file. See [Extending-Processes](Extending-Processes) "What the log tells you" and "From C#". | Your own `AssetsFinalize` validations against the now-final catalogues - e.g. iiex validates its casting patterns and roll sets here, since a bad one would otherwise fail silently the first time a player used it. Deriving `ExModSystem` calls your `OnAssetsFinalize` from here; there is nothing else to run at this phase. |
| `StartServerSide` / `StartClientSide` | `BlockNetworkModSystem.StartServerSide` captures `ServerWorld` and registers its 1000ms tick listener. `BlockMigrationModSystem`/`BlockEntityHealModSystem` (via `ChunkColumnSweeperModSystem.StartServerSide`) capture `_sapi` and register the `RunGame`-phase startup sweep plus the `ChunkColumnLoaded` listener. `ExConfigSyncModSystem` registers its channel on both sides and, server-side, subscribes `PlayerJoin`. `ExpandedLibModSystem.StartClientSide` runs `PreferenceRegistry.RegisterAll` (its own metric/imperial preference), then `ExPreferences.LoadConfig`, the handbook-units Harmony patch, a `LevelFinalize` hook that applies the local player's saved preferences, `CommandRegistry.RegisterAll` (the shared `.exmod` root), and `ExRecipeProfiles.ApplyAll(api)`. `ExpandedLibModSystem.StartServerSide` runs `CommandRegistry.RegisterAll` and `ExRecipeProfiles.ApplyAll(api)`. | Client: `PreferenceRegistry.RegisterAll(...)` **before** `CommandRegistry.RegisterAll(...)` (a sub-command resolves the preference it names once, at registration time). Server: `CommandRegistry.RegisterAll(...)`. Neither side needs to call `ExRecipeProfiles.ApplyAll` itself - exlib already applies every registered mod's profile on both sides. Deriving `ExModSystem` runs exactly this on each side (preferences before commands on the client) before calling your `OnStartServerSide`/`OnStartClientSide`. |
| Network manager's server tick (every 1000ms, registered in `BlockNetworkModSystem.StartServerSide`) | Resumes any connectivity review an unloaded chunk suspended (`ResumeSuspendedReviews`), then dispatches `BlockNetwork.OnTick` for every live network, `dt` capped at 2 seconds. | Nothing directly - this drives your own `BlockNetwork` subclass's `OnTick`, which is where your gameplay logic runs. |
| `PlayerJoin` (config sync) | `ExConfigSyncModSystem` sends one `ConfigSyncPacket` per section registered with `ExConfigProfiles` (every `Manageable` config) to the joining player, carrying the host's live values. | Nothing - a `Manageable` config gets this for free. A config with its own transport calls `IExConfigAccess.ImportJson` directly instead. See [Config-System](Config-System) "What the client sees". |
| Migration sweep and BE healer on chunk load | `BlockMigrationModSystem` and `BlockEntityHealModSystem` each sweep every already-loaded chunk once at `EnumServerRunPhase.RunGame`, then sweep each column again as it streams in (`ChunkColumnLoaded`). The migrator rewrites blocks/items matching any discovered `IBlockCodeMigration`/`IItemCodeMigration`/`IBlockRemoval`; the healer respawns a missing block entity for any block whose `EntityClass` resolves to a `[BlockEntityRegister]` type. | Declare your own `IBlockCodeMigration`/`IItemCodeMigration`/`IBlockRemoval`/`IBlockEntityMigration` implementations anywhere in your assembly - both systems discover them by reflection across every loaded assembly, no registration call needed. See [Migrations & Healing](Migrations-and-Healing). |
| `Dispose` | `ExpandedLibModSystem.Dispose` unpatches its Harmony instance. `BlockNetworkModSystem.Dispose` clears the graph (`_networks`, `_posToNetwork`, `_unreadableNodes`). | Unpatch your own Harmony instance and unregister any listeners you added directly (not through the registries above, which need no explicit teardown). |

## Ordering rules

Three rules the source above proves, not just conventions:

- **Preferences before commands, on the client.** A sub-command resolves the `IExPreference` it names
  once, at registration time, into a local it holds from then on. Call
  `PreferenceRegistry.RegisterAll` before `CommandRegistry.RegisterAll` in your `StartClientSide`, or a
  command naming your own preference finds nothing.
- **Register your network types in `Start`, before any node can initialise.** A node registers itself
  with the graph (`BlockNetworkModSystem.AddNode`) from block-entity initialization during chunk
  loading, which cannot happen before every mod's `Start` has returned. `RegisterNetworkType` called
  any later than `Start` risks a node reaching the graph before its type exists; an unregistered type
  logs an error and the block joins no network at all.
- **A def provider must be discovered in `Start` for the `AssetsLoaded` 0.04 injection to see it.**
  `EntityRegistry.RegisterAll` (called from `Start`) is what feeds `IExBlockDefProvider`/
  `IExItemDefProvider`/`IExRecipeDefProvider` implementors into `ExDefinitions`; `ExDefinitionModSystem`
  reads that registry at `AssetsLoaded` 0.04, strictly after every mod's `Start` has run. A provider
  whose owning mod never calls `RegisterAll` (or calls it only later) is never discovered.
