## 2026-07-31 — Design: layered charge (docs only, no code)

New design doc `docs/design/layered-charge.md`, indexed in `docs/design/README.md`. **Nothing built** —
this is a design brainstorm written down, not a change to the tree.

The question was whether the ore mixer's premixed burden is historically defensible. It is not: blast furnaces
were charged in **alternating layers** in every era, and the layering is load-bearing physics — only the coke
layers stay permeable in the cohesive zone, so a premixed charge chokes. The skip era combined ore + flux in
one skip and kept coke in its own, which is exactly the split the design adopts.

Two findings from reading the tree that the doc records, because both would be re-discovered painfully:

**The coal-pile collapse is not `UnstableFalling`.** Disassembling `VSSurvivalMod.dll` shows
`BlockEntityCoalPile.OnPlayerInteract → TriggerPileChanged → TryPartialCollapse` and the same from
`MergeWith`; `BlockCoalPile` never calls it. Both are **private on the BE** and fire on *interaction*, not on
neighbour removal — so stripping the JSON behaviour would never have fixed the column collapse that forced
top-down consumption (`BlockEntityBlastFurnace.cs:208-209`) and got per-layer temperature scrapped. One root
cause, both symptoms. Fix is a pile deriving from `BlockEntityItemPile`, the base *beneath* the coal pile.

**The shaft already averages the column** (`BlockEntityBlastFurnace.cs:266` discards position entirely), which
is arithmetically what a layered charge of separate materials gives you — so splitting coke out of burden
costs almost nothing in the heat model.

Design settled with the user across the session: burden becomes ore + flux; a burdenmaker (two hoppers + an
integrated bunker, no MP) replaces both the mixer and the ore bunker; `remeltburden` is deleted and the cupola
takes pig/scrap directly; one cell = one charge round carrying a coke band under a burden band; the furnace
becomes **counter-current** with combustion only at the raceway, so taller shafts and hot blast both reduce
coke rate without a coefficient; the crucible becomes live molten cells with iron under slag and typed taps
whose spout height *is* the pool cap. Cold furnace keeps its size; hot blast is the large one.

The cold-BF layout in `docs/design/layouts.txt` § 1 was edited by the user during the session (tuyeres up to
y=2, crucible widened to 3 and centred, both taps down to y=1); the doc records the code consequences
(`ShaftMin`/`ShaftMax`, `SolidifyCells`, `TuyereCells`).

⚠ Staged **after** the playtest build — it changes furnace pacing, and the bring-up wants player feedback on
pacing before pacing is built on top of.

Also added `docs/design/machines/ore-crusher.md` (**lpex**, indexed). Settled that the crusher is an
**mp-energy consumer**, not a self-contained steam machine as its reference engraving shows: harder ores then
become a continuous energy threshold rather than a tier flag, crushers stack as independent loads, and — the
real argument — a crusher is a **pulsed** load, so it is the machine that makes the flywheel *necessary* rather
than merely available. Being MP-driven does **not** put it in iwex; the forming-line rule
(iwex = MP / lpex = steam) governs variants of one machine, not which mod owns every MP consumer. Keeping it in
lpex is also what protects "nothing before cast iron requires power". It is throughput, never access — the
vanilla pulverizer route stays viable forever.

And `docs/design/machines/burdenmaker.md` (indexed), now that the art exists at
`assets/editable/shapes/machine-megablock-burdenmaker.json`. Footprint confirmed with the user at **9 cells**
(y=0 full 3×2 basin with the principal at its centre, y=1 front row only for the hoppers). Resolving the shape's
nesting shows the two hoppers land exactly on cell boundaries — large across x=−1/0, small on x=1 — so per-cell
interaction classification needs no geometry. Element groups double as the RCC stage list (masonry cheap first,
ironwork dear last), and `closed`/`open` are the idle and gate poses.

Later the same day the user drew `furnace-block-irontap`, `furnace-block-slagtap`, and reworked
`furnace-pipe-block-tuyere` and `furnace-megablock-hoppertall`. Added a **clay plug** section to
`layered-charge.md`: the plug is the closed state, wired as a per-BE bool → `SelectiveElements` → flow gate —
the same pattern the molten canal already uses for solidified cells — and it gives tapping a fireclay cost the
free right-click toggle never had. Also recorded the measured channel heights (iron 2/16, slag 10/16), the two
behaviours that geometry now decides for free (the slag channel *is* the overflow level; the two taps compete
for one volume, so neglected slag crowds out iron), and the decision to author taps **spout-out** with the 180°
applied at the shape rotation only — never in `TryPourMetal`, which stays pinned by
`BlastFurnaceTapTests.cs:160-178`.

**Late revision — the column stops being made of blocks.** The user proposed measuring each column by its
bands rather than its cells, and it is a straight simplification, so `layered-charge.md`'s charge-pile, column,
descent and charging sections were rewritten. A column `(x,z)` now owns an ordered list of **segments**
(material, units, temperature) and the furnace owns the columns; `iwex:chargepile` becomes a near-stateless
16-band **window** onto its column — no inventory, no `BlockEntityItemPile`, no per-block save, so vanilla's
`TryPartialCollapse` is not suppressed but absent. A round is the coke-to-coke span, free-sized, which retires
the cell-as-round / slice-as-round fork; 36 shaft BEs collapse to **9 segment stacks**; descent is one
subtraction; the working zone is a slice. This is the parcel-queue option rejected earlier, with its footprint
objection answered by making it per-*column* rather than one global queue.

Charging settled with it: **coke may only be added above the last burden**, each load filling the lowest
columns first. That one physical rule removes the need for a layer object (which would be stale after the first
melt cycle, since columns settle independently), a gate, and any overflow case — switching material starts a new
course by itself. Explicitly rejected: padding short courses to look full, because a cell that renders full but
holds less burden makes a yield drop uncauseable.

⚠ New open number: the slag notch at 10/16 makes the crucible 19 200 u against a ≈7 600 u campaign, so the
hearth would never back up. Recorded on the page — decide before the tap shapes are exported, since the notch
height *is* the cap.

⚠ Two export fixes recorded on the page, not yet applied (the shape is still editable-only): `open` needs
`onAnimationEnd: Hold` or the gate slides shut on its own — the same trap as the ore mixer's Gotcha 9 — and
`closed`, serving as the idle pose under RCC mesh suppression, must keep running or the block renders as
nothing. The `mp` marker was dropped from the filename by the user, since the burdenmaker has no MP.

## 2026-07-30 — iwex Stage 0 + Stage 1: buildable, and the pig loop unblocked

Executing `docs/internal/plans/iwex-bringup.md`. **All five suites green: 671 + 857 + 179 + 202 + 42 = 1951**
(iwex 844 → 857: 7 new goldens, 6 new tests).

**Stage 0 — nothing in iwex could be built.** Four blocks on the Stage 1 spine had **no recipe in any mod**,
which the audit had not caught: the **ore mixer** (the only source of burden — so a fresh world could never
charge a furnace), the **twin-tub blower** (the only air source), the **sand casting bed** (the only way to
turn molten iron into pigs), and the rolling mill. Added those, plus the mp-energy family (spur gear,
flywheel ×2, shaft, three transmission housings) which was entirely creative-only. Retargeted the tuyere from
`lpex:pipe-straight*` to `iwex:pipe-straight*` — one token, and lpex registers no straight pipe at all.

★★ **Three corrections came from the user mid-work, and each made the fix better:**

- **The ore mixer needs no gears.** It is driven by a *vanilla* wood axle (`BEBehaviorMPFillerPort`), not
  through mpenergy — so its RCC stage requiring `lpex:gear-iron` ×2 was wrong on the merits, not just on the
  domain. Now costs a rotor shaft + blades. ★ This is what makes the mixer the correct entry to the tier:
  buildable and operable with **no iwex prerequisite of any kind**.
- **The blower is vanilla MP too**, so the whole Stage 1 spine runs on wood axles — mpenergy is only needed
  by the rolling mill. Good scoping news.
- ⚠ **A bootstrap loop I nearly shipped**: gear → cast iron → cupola → remelt burden → **ore mixer** → gear.
  The gear's recipe must not require cast iron. It now has two routes — 2 iron ingots → 1 gear (wasteful
  bootstrap), or 1 cast-iron ingot → 2 gears once a cupola runs. Same "a working shop feeds itself, a new one
  pays retail" shape the puddling fettle already uses.

**Stage 1 — B14, B9, B10, B11 fixed with tests.**

- ★★ **B14, both halves.** The animator was built only in the client branch of `Initialize`, so `_animator`
  was null server-side and `TryCarveAt`'s guard always failed — **the bed could never be carved**. Every other
  constructed machine in the suite builds it on both sides with the comment *"resolved on both sides; it only
  builds/poses on the client"*; the bed was the lone exception. Second half: `OnCellInteract` was wired only
  through the filler path, and `FillerSlots` excludes offset (0,0) — which is exactly where the basin sits, so
  one slot was unreachable however you clicked. Added the principal's `OnBlockInteractStart`. Three new tests
  assert **every slot is reachable**.
- ★★ **B9, and its own failure mode.** `FlowEdge` moved the *whole* difference, overshooting the midpoint and
  swapping the pair (100/80 → 80/100) so it oscillated forever. Now moves half. ⚠ But halving alone
  **regressed a scenario test**: `MoltenMinFlowAmount` (10) became a *deadband of twice its size*, so a pair
  19 units apart moved nothing and a canal stalled partway along. Dropped the floor on levelling edges —
  integer halving is the better dribble control because it decays to nothing by itself. Three new tests,
  including one pinning the deadband.
- **B10** with a design correction: enabling all faces naively would let molten metal **climb**. Vertical
  edges are now **downhill-only**, driven from the upper cell, matching the pressure-valve idiom.
- **B11.** The pressure test now precedes the draw. An under-pressure main was drained dry every tick while
  the furnace credited itself zero supply — paying for air it never got and starving everything else on the
  main.

**⚠⚠ B2 withdrawn — it was wrong, and I nearly shipped a bad fix for it.** The arithmetic checks out
(standard burden settles at 1420 °C, break-even 23.94 % coke) but the furnace **already tells the player**:
`bf-info-heatstall` reads *"Needs {0} - add coke or hot blast"*, and the ledger shows T_process against the
melt line every tick. It is the documented "pay in coke" trade, taught in the UI. I had a curve shift costed
out and was about to apply it, which would have broken a working mechanic and perturbed every other furnace.
The lang string is what stopped it. STATE.md corrected; the real residual is a ~6 % band/threshold
misalignment, a tuning item.

**Also:** regenerating the goldens blessed **17 pre-existing stale ones** (slag texture, `castplate-heavy`'s
authored shape, cell sand basalt, a `BEBehaviorMoltenCell` filler) — real earlier source edits never
re-blessed, matching the known "stale-not-drift" note. Inspected each diff; all are source-correct.

**Fasteners settled** (user ruling, recorded in STATE.md): the "heading machine" was a euphemism and is gone.
**Nail machine** (strip → shear-and-head in one pass, as the real machines did) and **rivet machine**
(rod → cut-and-upset) are distinct blocks; **rivets move to iwex**; **no dies** and **no bolts**.

⚠ **Not done from Stage 1:** B16 (rotated cupola hopper columns) and D5b (one throughput number, four sites,
two hard-coded). ⚠ **And the mill is now buildable but cannot roll** — that is Stage 4; testers need telling,
or hold its recipe.

## 2026-07-30 — iwex bring-up plan, surveyed against source

New page `docs/internal/plans/iwex-bringup.md`, linked from README's *Read first*. It owns **the order iwex is brought
online in, the art queue, and the playtest gates** — nothing else, so it never competes with STATE.md
(blocker evidence) or the entity pages (numbers).

Driver: the decision to bring **one mod online at a time** for a playtest group, rather than moving between
mods. That changes the question from "which blocker is worst" to "what is the shortest walk to a build a
player can be handed", which the blocker list alone does not answer.

**Baseline verified, not assumed:** build green, **844 iwex tests pass**, 32 registered block classes, 81
runtime shapes, 397 lang keys × 3 locales in sync.

**Three findings that changed the plan:**

- ★★ **The art is mostly already drawn.** 87 untracked editable shapes sit under the new
  `<family>-<kind>-<name>` naming scheme while the runtime tree still carries the old exports. So the
  dominant art task is *export + wire*, and the genuine draw-queue is only **8 items** (shear, heading
  machine, stock rack, coke oven, crucible furnace, refractory pot, bolt, dies). Recorded as two separate
  lists so drawn art is not re-drawn.
- ★★ **B14 is the worst bug in the mod and the simplest.** `TryCarveAt` gates on `_animator?.IsConstructed`,
  but `_animator` is built only in the client branch of `Initialize` — so on the server it is always null and
  **the casting bed can never be carved**. No pig beds means the iron tier has no output at all. It has
  **zero test coverage** (one caller, no test references it), which is why 844 green tests missed it.
- ⚠ **Two STATE.md claims are wrong, both in our favour.** B3's stated cause ("no stock item carries a
  `stockForm`") is false — `StockItemDefinitions.cs:45` sets it; the real cause is that
  `WorkPiece.FromStack` reads only `stack.Attributes` and never falls back to the collectible's, so a fresh
  piece parses as null. And `BfIronPerMeltCycle` ships **60**, not 128 (128 is `HopperTallPileCap`).

**B17 also shrank.** The mill's footprint is already a correct 3×3 with both decks 3 filler cells wide; only
`Deck()` returns a single cell, pinning `AlongBarrel` to `[0.667, 1)`. Three lines, not a redesign.

**Also newly pinned as absent** (each verified by grep, not inferred): every rolled product item exists
*only* as a string literal in `RollSetItemDefinitions`; `RollSetSpec.OutputAt` is written and tested but
**called by nothing**, so the mill has no product-extraction path at all; and both reverberatory hearths are
racks with **zero temperature code** — the puddling and reheat processes were never written.

**Shape of the plan:** 6 stages, each ending at something a tester *does*. Stage 0 (4 recipe fixes) makes
iwex buildable without lpex; Stage 1 (6 bug fixes to live systems) closes ore → furnace → canal → pig and
**is the release** — the rest is depth on a working loop and ships as updates to the same group.

## 2026-07-29 — Design pillars corrected: the hands-on factory is the product; R7 is not "no GUI"

Maintainer corrected the framing the whole suite is designed against. Touches `overview.md`,
`conventions.md` R7, and `diagram-crafting.md`.

**★★ The engine of the suite: complexity goes into the BUILD, efficiency comes out of the OPERATION.** You
come all the way from casting iron into sand, through converters, to a rolling hall with steam hammers and
stamping — and the investment returns *speed at the lever*: a 3000 u cast slab is **eight feeds and five
stamps for fifteen plates**, where hand-forging fifteen is an afternoon even with a helve. ⚠ **So the mod
DOES optimise hard for fewer clicks — on the operating side.** The whole mill-and-stamp setup exists to avoid
hand forging. The rule is never to trade the two the wrong way: don't simplify the factory to save a build,
and don't add clicks to make a process feel weightier.

**★★ Operating friction is the currency the tech tree is denominated in.** Every upgrade buys down a
*specific, named* friction — hand forging → the mill; carry-back → the train; crop-and-head each → the cutter
bench; reheat trips → a bigger plant. So early friction must be **real and felt** (or there is nothing to
sell) and **removable by investment** (or there is no reward). ★ Historicity and hands-on feel are what make
the purchase legible, and that part is player-confirmed: the published `main` is far smaller and its machines
are expensive, yet what people praise is the feel of **running an actual factory** against vanilla's *light it
→ sleep → collect*.

⚠ **My first attempt at this pillar said "cost and tedium are features; never optimise for fewer clicks" —
that was wrong and was corrected immediately.** Tedium is precisely what the player is buying their way out
of. What my two rejected proposals earlier today actually got wrong was different and sharper: the cheap
fixed-gap "stand" instead of six real mills, and dropping the shear station, **both cut *build* complexity** —
the thing the player pays with and enjoys paying — not operating complexity.

**★★ "Cheap kickstart" answers a real reported complaint**, not an abstract entry price: the **enormous item
count needed to construct everything** (smex assumes plenty of iron, lpex is a bigger sink still), so there
was a mountain to climb before any result. The answer is **cast iron** — cast a few frames and `castplate`s
instead of hammering dozens of plates, and those make up most of a machine — plus **throughput**: blast
furnace ≈2× a bloomery, plus ore roasting. ⚠ Recorded explicitly that **the machines still cost a ton of
iron**; nothing became materially cheaper, the iron just became faster to produce and the parts faster to
make — consistent with the standing rule that **industrialisation buys labour, never material**.

**⚠ R7 "No GUI" is retired — it was an absolute that did not survive contact with the mods.** Every machine
has status UI; temperature, pressure and pipe contents are readable by looking; and **full-window UI machines
already exist** (design table, boring machine) with more likely. Rewritten as **R7 — Nothing is hidden**:
state must be legible to a player standing in front of the machine, operation stays in-world and verb-based
(you work the machine, not a menu), **windows are allowed** where the interaction needs one, and what is
forbidden is *state you cannot see* — no hidden timers, no invisible buffers, no "trust it". ★ `diagram-
crafting.md` had framed its two windows as a **sanctioned exception** to R7; under the new wording they are a
straightforward *case* of it — a catalogue of two dozen plans is more legible in a list than in block-info.
Existing `(R7)` citations elsewhere still read correctly against the new rule.

## 2026-07-29 (end of day, revised ×2) — The shear is MP and its own machine; the hammer never sheared

Two more maintainer corrections, both right, and the second one was a genuine research catch.

**The shear is MP-driven, not hand-worked.** Almost everything else in the mod is MP, and parting a plate is
not a thing arms do. ★★ The references never suggested otherwise either — **every shear on the 1867 plate has
a gear train and a flywheel**, not one is hand-worked. Fig 5 (double shearing machine) is the shape to draw:
heaviest, most legible, and its giant flywheel is the right visual promise.

**⚠⚠ The steam hammer never sheared — several earlier passes had that wrong.** A steam hammer is a *forging*
machine (Nasmyth 1839, for a paddle shaft): drawing down, upsetting, later die forging. **Shearing was always
a dedicated machine**, and the 1867 plate names three on one page — bar shear (3), punching and shearing (4),
double shearing (5); the boiler-shop and mill-hall standards. A hammer *can* part bar with a hot-set chisel,
but that is hand tooling under a hammer, not a shear. ★★ **The replacement distinction is one line: the shear
cuts *across*, the die cuts *out*.** Shearing = straight-line parting, pure force, no form → the MP shear.
Blanking/stamping = punching a *shape* out of a strip, the die imparts geometry → the steam hammer. ★ The wide
route's payoff is untouched: 15 × 1 × 16 does not partition into 9 × 9 by straight cuts, so `boilerplate` → 3
plates genuinely *is* blanking and genuinely *is* the hammer's job. The hammer loses only something it never
historically had.

**★★ Cold shearing now gates on `MinTorque`, not on a tier.** With the shear its own MP machine the LP/HP
hammer gate is the wrong axis — what decides a cold cut is **force**. Hot/thin is cheap; cold costs much more;
the **large flywheel (≈15× energy) is the practical unlock**. Better in three ways: continuous instead of a
step, **no second block and no mod dependency**, and it finally gives the large flywheel a *second job* beyond
buffering the mill. ★★ The payoff the tier gate existed for survives intact — **a big enough plant means fewer
trips to the reheat furnace** — but now it comes from infrastructure every player builds. ⚠ First real use of
`RollSetSpec.MinTorque`, currently parsed/stored/never consulted. ⚠ `ColdShearMaxThickness` is deleted from
the design entirely (it never existed in config).

**All three benches move to `mpenergy` with cast-iron shafting** (maintainer) — ⚠ my "vanilla MP, wooden
axles" call was wrong on both counts. ★★ **Cast iron is the shared prerequisite, so there is no second tier to
gate**: every one of these is a cast-iron frame, and cast iron is what unlocks `mpenergy` itself. ★★ And
`mpenergy` is the *correct* network, not merely the one we have — **all three are pulsed loads** (a shear
takes one bite; the nail machine's crank is a shear per stroke; the rivet machine's blow is a hammer blow),
and punch presses and shears are the textbook reason a shop has flywheels at all. That is why every figure
draws one, and it is what lets a row of them run off one shaft without dragging it down — **the art explains
the mechanic**. ★ Verified the kit is **already built**: `BlockCastIronShaft`, `BlockCastIronBevel`,
`BlockTransmission`, `BlockFlywheel` (an older note claiming the drive infra was missing is stale). At 1 × 1
each machine is simply its own `BlockNetworkNode` — no filler, no multiblock.

## 2026-07-29 (later) — Four corrections: area-based heat, six *ordinary* mills, the half-step, no lopsided art

Maintainer corrected four things from the close earlier today. Docs updated; three of the four **remove** work.

**Heat scales on contact area, not mass** — "heat exchange speed is defined by area of contact". So soak time
∝ **`V/A`**, which reduces to `t/2` for a plate and `t/4` for a square bar: thickness exactly, section falling
out on its own, and nothing new to track. ⚠ **This kills the ×2 furnace multiplier**, which was set for the
mass law: under an area law ×2 puts *every* piece below a vanilla ingot's forge time, cast slab included, and
the reheat stops being a beat. Recommended **×1** — the furnace's argument was never speed, it is that **a
forge cannot hold a slab at all** and the hearth soaks two or three at once. ★★ The real payoff is that **the
same `V/A` drives the cooling**: feed `RollingPass.Cool` a rate of `k·A/V` and one constant governs both
directions. A cast slab at 4 thick soaks slowly and holds heat; at 1.0 it reheats in 0.9× an ingot and sheds
heat ~3× faster — so a schedule **accelerates and tightens as it goes**, ponderous at breakdown, frantic at
finishing. ★ It also lands the wide route's argument a third time from physics: thin stock cools fastest *and*
needs the most strips on a narrow barrel, so the narrow route's last gaps are the worst of both.

**No cheap "stand" block — six *ordinary* mills.** ⚠ My simplified fixed-gap variant is rejected, and the
reason is the design's, not an implementation one: **building a literal iron rolling plant should cost like
one.** A player who does not want the hall re-tools fewer mills and pays in handling — capital against labour,
the trade the whole mod is made of. ★★ And it is what a mod is *for*: Vintage Story makes a single ingot
precious, so making industrial **scale** reachable is the point, and shrinking the hall into one clever block
would quietly delete it. Bonus: six mills needs **no new code at all**.

**★★ The `.75` / `.25` stages are the mid-state of ONE gap, not gaps of their own.** 2.0 fed at the 1.5
rollers → **1.75**; fed again → **1.5**. So **a gap = two rounds**: round 1 lands the half-step, round 2 lands
the gap. Same feed count as before, but the metal moves on *both*. ⚠ Corrects my "a pass removes 0.25" rule
and, with it, my reading of 2.25 as a stopping point — see below.

**Left/right lopsided shapes dropped; alternation is a click count.** A wide piece needs one RMB per side per
round, ★★ and because a round only completes when **every** side is fed, after round 1 the *whole* piece sits
on the half-step — so there is **one shape per half-step and no lopsided variants**. Four feeds for a wide
piece, none of the art. ★★ It also deletes an axis of `WorkPiece` state: `Strips: float[]` + `Turned: bool[]`
→ one `Thickness` + a per-side fed-this-round flag, and `StripWidth` / `StripLength` / `Thickest` /
`Thinnest` / `IsEven` / `Resplit` all go. The half-step carries the "half-rolled" reading instead. ⚠ Pinned:
sides compute on **entry** width (that is why the bar's last gap costs 4, not 6), and the round **resets** on
a different barrel.

**★★ Consequence — the rod fixes both stock lengths, and the billet must crop mid-gap.** With 2.25 demoted to
a half-step, the derivation changes: `shingledbar` 18 crops at **2.0** (L = 40.50 → 4 rods) and `castbillet`
27 crops at the **2.25 half-step** (L = **48.00 exactly** → 6, each finished to 2.0). Carried to 2.0 the
billet would be **60.75 long** — past the hearth in both seatings *and* above cold-shear thickness, the exact
soft-lock the invariant forbids. ★ So **the half-step is load-bearing, not decorative**: it is a legal place to
leave a piece, and the cast tier's whole schedule depends on stopping there. ⚠ Which strengthens the build-1
finding — the shear must accept half-steps, so `Outputs` keying on *stage* is not optional.

Verified by hand: flat schedule for the bar is 2 + 2 + 4 + 4 = **12 feeds** to 9 × 1 × 18 = 162 vx³ = 2 plates,
matching `item-beam-rolled.json`'s `CutPlate1` exactly; the barrel first bites at 4.5 wide, halfway through.

## 2026-07-28 — The stock stage-shape idiom is proven; spread turns out to belong to the roll set

Measured the maintainer's re-authored `item-shingled-bar` + `item-beam-rolled`. **Call it proven.** Every
stage holds volume (162.0 / 166.4 / 162.5 / 162.0 / 160.0 grooved; 162.0 at all five flatten stages), the
2.25 stage lands on **exactly 32.0 long** so the cut at 2.0 is forced rather than chosen, and ★★ the leaf
geometry **is** the vanilla item: `Plate1` is 9 × 1 × 9, which is precisely what
`survival/shapes/item/plate.json` measures. The flattened bar at the 1.0 gap is two vanilla plates end to
end, not an approximation.

★★ **Spread is a property of the roll set, not the stock.** The grooved route holds `w = t` and puts
everything into length (18 → 21.4 → 25.9 → 32.0 → 40.5); the flatten route holds **length fixed at 18** and
puts everything into width (3 → … → 9.0, which solves to `e = 1.0` exactly). `StockForm.SpreadExponent`
cannot express that — it makes spread a property of what you are rolling rather than what you are rolling it
*with*. It moves to `RollSetSpec` as a section mode (`square` | `flat`), and `SpreadWidth` needs a square
branch. It also yields the mill's cleanest player rule: **grooved draws, flat spreads** — so grooved stock
needs cutting and flat stock never does.

★★ **The cut-stage ambiguity is closed by a naming convention** the maintainer then adopted: cut stages are
prefixed **`Cut`** (`CutRod1`, `CutNailRod1`, `CutPlate1`), so an element's *name* says whether its children
are products or the two halves of one piece. Re-measured after the fixes, every cut stage matches its parent
exactly — `CutRod1` 4 × 40 = 160, `CutNailRod1` 4 × 10 = 40, `CutPlate1` 2 × 81 = 162 — so
`children(Cut*) == mass / productMass` is now mechanically testable.

Intermediate stages deliberately do *not* conserve volume precisely (`Grooved275` is +2.7 % because 22 is a
rounder length than 21.4). That is correct: an intermediate is never a stopping point, carries no mass, and
code sets the rendered length. Only the base and the `Cut*` leaves are load-bearing, and those are exact.

**Nail ladder settled at 25 u:** bar 400 → 4 rolled rod @100 → 4 nail rod @25 → 1 `metalnailsandstrips` each.
`4 × 4 × 25 = 400 u`, conserved to the unit — and 4 nails per 100 u is *precisely* vanilla's anvil rate, so
the mill cannot mint a unit against the hand route. ★ That leaves the nail machine no yield to win, so its
advantage becomes **skipping the intermediate**: feed it a whole rolled rod and it slits *and* heads in one
operation, against cropping four nail rods and heading each separately by hand.

**`pig` = 375 u** (bed impressions measure 5 × 3 × 10 = 150 vx³), and the maintainer chose the second option
for the charge: ★ **it is not lossy, it is split** — 9 pigs (3375 u) → 8 bars (3200) + 175 u of tap cinder,
cast to slag bricks in the same bed. Nothing is destroyed, the 8–12 % band stops being a constraint the
numbers must hit, and R6 stays exact through the one process that would otherwise have to break it.

**The 32-voxel limit is the reheat hearth's depth** (3 cells × **2** cells, 2 × 16 = 32) — so derive it from
the footprint, and a deeper reheat furnace becomes a real upgrade. ⚠ `heatinghearth.json` draws its stock
beds one cell deep (16), so the art and the limit disagree today.

**Coke oven charging: `iwex:hopper-tall`, not a trapdoor.** ⚠ Vanilla's trapdoor has **no facing in its block
code** (variantgroups `style`/`material`/`age`; `entityBehaviors: [{name:"TrapDoor"}]`) — it is the one block
the oriented-parts check cannot verify, so a layout can require it and still complete with the hinge wrong.
`hopper-tall` is `StructureAngle => 0`, has nothing to misplace, and is **already** the charging block of the
cold blast furnace and the cupola. Same answer for charging ore into the heating furnace for roasting: hopper
for bulk, hearth fillers for pieces.

★ The hopper is open storage, so the crown still needs a lid: **`iwex:ovenlid`, a third def on the charge-door
chassis.** `BlockChargeDoor` already emits two blocktypes from one class with clips in block attributes and
`BlockEntityChargeDoor` already exposes `MainOpen`/`IsVenting`, so it is a shape and an entry. Its facing
lives in the **block code** (`ovenlid-north`), so the legend auto-detects it, the layout rotates it, and the
orientation check verifies it — everything the trapdoor cannot do. ⚠ Do not fold it into `hopper-tall`: that
block is deliberately `StructureAngle => 0` and already ships inside two furnace layouts. The state then
earns its keep — **lid closed = coking, lid open = charging or burning**.

★★ **The reheat hearth must stop authoring stock.** `HeatingHearthLayout` names one element group per
(row × form) — 3 × 5 today, and the rolled ladder makes that combinatorial. It also does not need to exist:

prune to the same stage literal the held item uses, `Translate` into the row slot, and rotate **once** at the

remap is the precedent).

## 2026-07-28 — The density rule: 1 vx³ = 2.5 u, measured off vanilla

Measured the solid volumes of vanilla's own shapes against their melt-back: `ingot` 3×2×7 = 42 vx³ / 100 u,
`rod` 2×2×10 = 40 / 100, `metalplate` 9×1×9 = 81 / 200. **2.381, 2.500, 2.469 u/vx³ — mean 2.45, spread
±2.5 %.** So mass can be *derived from geometry* across the whole mod instead of picked per item.

This corrects the previous entry, which called the rod "absurdly heavy relative to its size". It is not: at
40 vx³ against the ingot's 42 it is almost exactly an ingot's worth of metal, drawn to match. The reading was
wrong, not vanilla.

The maintainer then fixed two products — **1 bar → 2 `metalplate`** and **1 nail rod → 2
`metalnailsandstrips`** — and vanilla's 200 and 25 force the rest:

**bar 400 → 4 rolled rod @100 → 2 nail rod @50 → 2 nails @25.** `4 × 2 × 2 × 25 = 400 u`, conserved to the
unit. ★★ `400 / 50 = 8` over two cut stages factors as 4 × 2, which lands the middle term on **100 u — exact
`game:rod` parity, at exactly `game:rod`'s own 2 × 2 × 10 geometry.** Nothing chose that.

★★ **And the 32-voxel handling limit derives the cut counts.** Length is `V / t²` for a square section: the
bar (3×3×18 = 162 vx³) runs 18 → 21.4 → 25.9 → **32.0 exactly** at the 2.25 gap, then 40.5 at 2.0 — over,
so it must be cropped, and cropping into 100 u pieces gives **four** at 10 long. The rod (40 vx³) runs to 40
long at the 1.0 gap, over again, and cropping into 50 u pieces gives **two** at 20 long. Neither count is a
choice.

⚠ Art deltas: bar 3×3×16 → **18**, rolled rod 2×2×12 → **10**, nail rod 1×1×18 → **20**.

**The shear crops one product off the end rather than converting the piece** — the ladder above divides
perfectly, but part-rolled and cast stock would otherwise need a rounding rule.

**Nail machine:** vanilla's anvil route is 1 ingot → 4 nails-and-strips (exact), so 25 u is a hard ceiling
nothing may beat. ★ The machine's reason to exist is therefore that the *hand* route is lossy — shears crop
1 nails-and-strips from a 50 u nail rod, the machine shears **and heads** and gets 2. Small MP bench block
with swappable die tooling (the `rollset`/`pattern` idiom), not the steam hammer: the cut-nail machine is
1786–95, contemporary with puddling, and gating nails behind the forming shop puts the cheapest fastener in
the game behind the most expensive machine. ⚠ Vanilla's 54-voxel nail pattern outputs 8 from one ingot —
200 u out of 100 — do not copy it.

Recorded in `iwex.md`. Open: the `pig` art (file draws 5×3×12 = 180 vx³ → 450 u, stated 5×2×10 → 250 u).

## 2026-07-28 — Casting bed: four rows, one mold, 20 castings; the sand step leaves the cell cycle

Both halves are the maintainer's decisions, taken against the re-authored `molten-megablock-sandbed`
shape. The shipped `casting/sandcastingbed.json` was still the **three-row** conversion, so it was

## 2026-07-27 — Furnace hierarchy: melting made optional; heating furnace built

**The refactor turned out to be far smaller than the fork suggested**, because reading the tick showed the
core *already* degrades gracefully for non-blast furnaces: empty tuyere/outlet lists make those loops
no-ops, and `RequiresBlast=false` opts out of starvation. Blast was already a parameter. The only genuine
blocker was the molten-product half.

So instead of splitting a 1398-line live class (3 furnaces depend on it), the six product members became
**virtual with defaults that are true rather than stubbed**:

- `DrainedMetalUnits => 0` - and `SolidifyBottomLayer` already returns on `units <= 0`, so the whole
  freeze path short-circuits and `SolidProductBlock`/`StampSolidProduct`/`ClearMoltenPools` are never
  reached. A furnace with no pool freezes no residue: a fact, not a stub.
- `LiquidCapacityReached => false` - nothing pooled can never back up.
- `DrainProducts` - no-op; no pool, no taps.

The distinction that matters: the defaults sit at the **base** and are semantically correct, rather than
each non-melting subclass writing six lies. The base stopped *demanding* melt behaviour, which was the
actual complaint.

Also **lifted the charge-pile walk** from `BlockEntityBlastFurnace` (private) into the core as
`CollectChargePiles()`. It reads `ShaftBounds()`, which is why a reverberatory furnace needs no special
case: it declares the **firebox** as its bounds and the same walk finds fuel beside the hearth instead of
under the charge. Separating fuel from work is a coordinate change, not a different machine.

Built on it: `iwex:heatingfurnacecore` + `BlockEntityHeatingFurnace` - the first furnace with no molten
pool, no tap and no product to freeze. Overrides **none** of the product members. Its firebox reads as pure
fuel (`BurdenMix(0,0,count)`), which is the honest heat-balance input for a fire that reduces nothing.

Structural shells only: both furnaces stand, light, burn and hold heat. Not built - the puddling cycle
(fettle/charge/rabble/ball), the heating hearth's typed rows and access rule, and roasting.

it never stalls waiting for one), no tuyeres, no gas outlets. Structural shell only - the puddling cycle
(fettle / charge / melt / rabble / ball) is not built.

**Fork surfaced, not guessed: the heating furnace does not fit `BlockEntityFurnaceCore`.** The base has 17
abstract members and ~6 of them are molten-product machinery (`DrainProducts`, `SolidProductBlock`,
`DrainedMetalUnits`, `StampSolidProduct`, `ClearMoltenPools`, `LiquidCapacityReached`). The heating furnace
melts nothing - it only raises stock temperature - so inheriting means stubbing those as no-ops. The shared
piece it actually wants is **firebox + heat balance + FSM**, which sits *below* the melt machinery. Held for
a decision rather than force-fitted, since it shapes both furnaces and is expensive to undo.

## 2026-07-27 — Tier axes: recovery is spent once

Added `conventions.md` § "Which tier moves which number" to the recovery model, answering whether hot blast
and the open hearth should raise iron yield. **No - and the reason is structural: recovery is bounded** (it
cannot exceed what the ore holds), so stacking "+recovery" across five tiers drifts everything toward the
ceiling and leaves the late tiers nothing to give. Spend it once, on the blast furnace's gap over the
bloomery, and let later tiers compete on unbounded axes (fuel, throughput) or categorical ones (quality,
scrap tolerance).

Both are already designed that way, which is worth recording so nobody "improves" them later:

- **Hot blast** is historically a *fuel* upgrade (Neilson cut coal by ~2/3), and smex already states it
  without a hidden multiplier - a **low-coke burden becomes viable**, which IS the fuel saving expressed as
  a change in what you may charge. Its throughput gain is already emergent from the heat balance's
  temp-margin term. Nothing to add.
- **Open hearth** wins on what the Bessemer structurally cannot do: hours-long heats that can be sampled and
  corrected, external flame so it swallows bulk scrap where the autothermal Bessemer chokes at ~15-20 %, and
  no air through the metal - the low-N identity smex already builds its material tiers on. It is the one
  later tier allowed a recovery edge (~94 % vs 90 %), earned honestly: no blow means no spitting or fume.

Also noted the redundancy risk between roasting and hot blast (both cut fuel) and the distinction that keeps
them separate: roasting acts on the **charge**, hot blast on the **furnace** (`T_in`) - different terms of
the same equation.

## 2026-07-27 — Metal-recovery model written into design; **invariant R2 revised**

Recorded the recovery/material-loss model in `conventions.md` § metal recovery. The idea: **vanilla's 5 u
per nugget is not the ore's iron content, it is a bloomery's share of it** (~50 % historically), so the rock
holds ~10 u and a blast furnace recovering more is not inflation. The anchor derives itself - pick the
bloomery's recovery from history, and vanilla's own number gives the true content - so every figure is
arguable from metallurgy instead of tuned by feel. Vanilla stays untouched and yet its historical 40-60 %
loss ends up modelled, purely by being the floor.

**This contradicted R2, so R2 is revised, not appended to.** It said "mass-conserving, no hidden yield loss
... 1 u in -> 1 u out ... tiers differ in throughput and fuel cost, **never material yield**" - the exact
opposite of what we now want. New R2 keeps what was valuable (predictable, never random, nothing hidden) and
inverts the mechanism: transport/casting/forming/distillation/chemistry stay 1:1, **reduction and refining
declare a recovery fraction**, and the shortfall must become a by-product the player can see and use.

R2 is referenced by name from six docs, so I checked each. Two were actually wrong and are fixed:

- `iwex.md` puddling claimed "9 pigs -> 18 balls, mass-conserving" - now notes the puddling loss.
- `smex.md:18` claimed "all melt/refine steps are mass-conserving (R2)" while **`smex.md:57` in the same
  document** already specified 100 u pig -> 90 u steel + 6 u slag + 4 u gas. Self-contradictory before this
  change; now reconciled.

The rest (materials.md billet splitting, elex chemistry, lpex distillation) are forming/chemistry and stay
1:1 under the revised rule.

Also recorded: the roasting decisions (own item; smelts in a vanilla bloomery via the `combustibleProps`
trick smex already uses on `crushed-iron`, so roasting is not a trap; mixer accepts both raw and roasted, or
iron deadlocks behind cast iron), and the **blocking gap** - the blast furnace has no mass balance at all
(`BfIronPerMeltCycle` is a flat rate, burden stores fractions not units), so recovery fractions need charge
accounting built first. Numbers are explicitly flagged placeholder: balance once the furnaces run.

## 2026-07-27 — Fettle stock: tap cinder + mill scale, one tag, three interchangeable parts

The fettle recipe is now **three parts, each any `fettlestock` material**: `game:crushed-iron`,
`iwex:tapcinder` (raked out when the puddling hearth is cleaned) or `iwex:millscale` (a rare drop off the
running mill). Three in, three out.

That interchangeability is the mechanic, not a convenience: a first batch is three parts bought ore because
that is all a player has, and each part gets displaced by oxide the machines gave back until fettling costs
no ore at all. **A working shop feeds itself; a new one pays in ore.** It also means the losses have somewhere
to go, which was the rule - nothing silently drains.

Neither recovered oxide is craftable. You get them by *running* the machines, which is what makes the
displacement real rather than a second recipe.

Mechanism: an item **tag**, since a tag is the only way one recipe slot accepts several unrelated codes
(vanilla's own `tool-chisel` / `flux` work this way). Added `IngredientBuilder.Tagged(type, tags)` to exlib.
`game:crushed-iron` is tagged by a patch using **`tagsByType`** (`assets/iwex/patches/vanilla/`) - NOT a
top-level `tags` array, because `crushed.json` is one itemtype covering every ore and crushed galena must not
fettle. The `"*": []` catch-all mirrors vanilla's own `powder.json`, which tags only borax as flux the same
way. Tag name is unnamespaced, following vanilla, so another mod can add a fettle material without touching
iwex.

## 2026-07-27 — Sand bed: carve/break interaction + carved-channel flow; slag texture shipped

**Carving is now the gameplay, because flow is gated on it.** A `FlowEdge` only exists where **both** ends
are carved, so metal runs exactly where the player cut it and stops dead at a mold they have broken open.
That gates the *edges*, not the cell list, deliberately: a stranded charge must still tick thermally and cool.

- RMB a spine cell -> runner channel; RMB a flank -> pig mold; sneak-RMB a flank -> brick mold.
- Harvesting **breaks the impression**: the slot drops to plain sand and stops conducting until re-carved.

class of bug where the carved surface and the filler cells disagree about where a slot lives, and it means

## 2026-07-27 — Composed work-piece mesh: the mill is feature-complete

A part-rolled piece now *looks* part-rolled in the hand - thin and wide down the side that has been through the
rolls, thick and narrow down the side that has not. That matters because the player carries the piece between
every pass, so its state has to be legible without a tooltip.

The mesh is **composed, not authored**: the form's one base shape is tesselated once and scaled per side from
the *same numbers the simulation uses* (`WorkPiece.StripWidth`/`StripLength`). Two consequences: the art cannot
drift from the behaviour, and the whole schedule costs one shape per form instead of one per state. Cached by
geometry alone, so it is a handful of entries per form rather than one per stack.

`StockMesh` is pure and tested because this is arithmetic that **fails quietly** - a side placed slightly out
reads as a modelling slip, not a bug, and nobody would think to check it. Pinned: sides abut exactly (the seam
is what sells it as one object), the piece stays centred however lopsided, and the worked side really is the
wider one. The final look still wants an in-game eye, as every held transform here does.

`PassesAt` is **kept**, not retired: with sides now barrel-dependent it is the check on the emergent count
rather than dead weight.

## 2026-07-27 — Barrel-dependent strips, and much simpler jamming

**The strip bug.** `WorkPiece.StripCount` was a constant 2, which conflated "the two halves a wide piece is
rolled in" with "the two passes a gap takes". Result: every gap cost 2 feeds whatever the roll set, so **the
wide roll set had no advantage at all** - the whole point of it. Now:

- **Sides are the piece measured against the barrel**: `ceil(width / barrelWidth)`. A wide set swallows the
  piece whole (1 side); a narrow one takes it a side at a time once it has spread.
- **Each side takes two feeds** - a pass, then turned over and passed again. So a gap costs `2 × sides`:
  **2 on wide rolls, 4 on narrow ones**, which is what was asked for originally.
- A piece is re-divided for whatever barrel it meets (`Resplit`), and an *uneven* piece is left alone - it
  simply fails to bite at the next gap until its sides are levelled. The maintainer's point: no special case
  needed, the consequence handles itself.

**Jamming, simplified to one rule.** Whatever stops a pass - the drive dies, or the stock drops below rolling
heat - the pass **freezes where it is**. The player restarts the line, or **wrenches the piece out**. Either
way the piece comes back **exactly as it went in**: the reduction is now applied only on completion
(`CompletePass`), never on the way in, so an interrupted pass never leaves half-rolled stock and that gap is
simply redone. This replaced the older resume-where-it-stopped behaviour.

★ **`TooCold` split from `WontBite`.** Both fail the same bite check, but one is fixed at the furnace and the
other at the barrel - and a player can only learn the schedule if the two read differently.

⚠️ **`RollingCoolRate` 0.02 → 0.005.** At 0.02 a piece dropped under rolling heat *mid-pass* (675 °C after a
25 s pass), so the freeze made the mill read as broken. At 0.005 a pass finishes comfortably (973 °C) while a
full schedule of round trips still cannot be done on one heat - reheating stays routine, which is correct.

Test note: passes must be advanced at a realistic `dt` (0.25 s). A single huge `dt` cools the piece to a
standstill in one step, which is an artefact of the test, not the machine.

## 2026-07-27 — Block-level wiring: the mill is playable

`BlockRollingMill` now implements the real `IFillerInteractionTarget` routing (the four Phase-A stubs are gone):

- **Holding a roll set, anywhere on the machine** → fit it, handing back whatever was there. Refused mid-pass,
  and the set is put back in the player's hand rather than eaten if the fit fails.
- **Holding stock on the INPUT deck** → feed it. `HitPosition` (which survives the filler repoint) is rotated
  into the mill's authored frame and mapped along the barrel, so **where you click picks the gap**; **sneak
  picks the strip**. The piece leaves the hand, rides through, and lands on the far deck.
- **Clicking the output deck does nothing** - a two-high stand cannot be fed backwards, which is the whole
  reason for the carry-back.

Every refusal gets its own message rather than a shared "nothing happened": no roll set / wrong stock / gap too
wide (passes through untouched) / skids (too deep, or gone cold). Those are genuinely different mistakes and
the player can only learn the schedule if they read differently. Lang in en/ru/uk, plus the stock item names
and two interaction-help lines.

## 2026-07-27 — Zones, strips and the roll-set slot: the mill works end to end

`MillFeed.Decide` is the pure rule set for offering stock to the rolls, in the same shape as the casting
cell's `Decide`. The player picks two things at the deck — **where along the barrel** (which gap,
`GapZone(alongBarrel, gapCount)`) and **which strip** (plain click = near, sneak = far) — and everything else
follows from geometry.

★ **There is deliberately no "that is not the next gap" rule.** Skipping is stopped by `δ_max = μ²R`: a gap far
narrower than the stock simply skids. So the schedule is enforced by the *same relation that makes this a hot
mill*, and an operator who spots a legal deeper bite may take it and pay in torque (from 2.0, the 1.0 gap is
exactly δ_max, so skipping 1.5 is allowed). A gap that is too **wide** is not an error either — the piece
passes through untouched, a wasted walk that teaches itself.

`BlockEntityRollingMill` gained the **roll-set slot** (the machine's one real configuration; cannot be swapped
mid-pass, returned when the mill is broken) and `TryFeed`, which reduces the chosen strip, sends the *already
rolled* piece through, and returns the verdict so the caller can say **why** nothing happened — a skid and a
too-wide gap are very different mistakes. Also `StockForm.BaseLength` + `WorkPiece.StripLength`, so a
well-worked strip is longer and visibly takes longer to feed.

Still to do: the composed per-stack mesh for partial flattening, and retiring `PassesAt` now that the count is
emergent.

## 2026-07-27 — The work piece, and feeding it through the mill

The maintainer's interaction model, which is historically exact: a two-high stand **cannot be fed backwards**,
so the piece goes in one deck, through the rolls, and lands on the *opposite* one — the player then walks
round, picks it up and feeds it again. That carry-back was the defining drudgery of early rolling and is why
three-high and reversing mills were later invented.

- **`WorkPiece`** — form + a thickness per **strip** across the width, carried on the item stack, because the
  piece spends most of its life in the player's hands or on the ground rather than in the machine. Strips are
  what let a half-rolled piece exist: thin and wide down one side, still thick down the other. Guarded
  invariant: **each strip spreads on its own share of the base width and ceiling, so summing them reproduces
  `StockForm.WidthAt` exactly** — otherwise half-rolled geometry and the shipped stage shapes drift apart.
- **`StockItemDefinitions`** — one item per form, `maxstacksize 1` (each piece carries its own state, so they
  must never merge), heat on vanilla's temperature attribute so it keeps cooling during the carry-back. That
  turns the walk into a **heat budget**: dawdle and the next pass loads harder, or is refused outright. It also
  gives the reheat furnace its job and makes mill layout matter.
- **Feed and eject** — `BeginPass` now takes the stack, and completion drops it on the output deck with a
  near-zero velocity (it should sit there, not bounce off behind the mill). A jammed piece is handed back when
  the mill is broken rather than swallowed.
- **Drive direction** — the mill's feed side follows the rolls, so reversing the drive swaps input and output.
  That needed direction to survive into the network: our MP port took `Math.Abs` and the mpenergy state clamps
  ω to `[0, max]`, so the sign was being thrown away. Added `BEBehaviorMPFillerPort.IsReversed` and a new
  `IMpEnergyDirection` node interface feeding `MpEnergyNetworkState.Reversed`. **Magnitude stays unsigned** —
  the whole torque balance is magnitudes and signing ω would complicate every relation for one machine's sake.

⚠️ Test-harness note: the harness's ModLoader does not hand back the graph manager, so a block entity's
`NetworkSystem` is null unless set by reflection (the transmission tests already do this). Without it every
drive-direction question silently answers "forward".

## 2026-07-27 — Stock sizing corrected (maintainer feedback)

Three corrections to the generated stages:

- **Length is no longer capped.** The earlier 1.5× cap was the wrong trade — an oversized held item is fine
  (vanilla has the player carrying 3×3 gate blocks), and items in hand can be scaled. Length is now whatever
  conserving the volume demands, computed off the *actual* (possibly capped) width, so once a piece stops
  widening every further reduction runs out lengthways (bloom ×2.25, slab ×3.43 at the last gap).
- **Width is capped per form** — bloom **8**, slab **14**, sized to fit inside the rolling-mill model.
- **The bloom reaches nearly its full width at the 1-voxel gap**, because one voxel thick × ~8 wide is the
  proportion of a vanilla metal plate, which is what the piece gets cut into. The schedule now lands the stock
  *on* plate geometry rather than near it.

That required a **per-form spread exponent** (`StockForm`) rather than one shared √ — which turns out to be
physically right anyway: spread falls as stock gets wider relative to its thickness, because friction across a
wide face resists sideways flow while a narrow bar has nothing holding it in. So the bloom (entering square)
spreads hard at e≈0.85 and the slab (already 2.7× wider than thick) mostly draws out at e≈0.46.

Knock-on: the flat set's barrel went 4 → **6** to keep a real cost gradient (the schedule now runs 2, 2, 4, 4
passes rather than 4 across the board), and the wide barrel 20 → **16**, which still clears every form's
ceiling. `RolledStockStagesTests` now checks length as well as width and thickness.

## 2026-07-27 — Rolled-stock stages generated from the authored bases; pass count from spread

Stock stages are **generated** from the two authored bases (`item-shingledbloom`, `item-shingledslab`) rather
than drawn one by one: `scripts/generate-rolled-stock.py` flattens the base to each gap in the schedule.
Thickness is exact and width follows the same spread model the simulation uses, so the art and the pass count
cannot disagree. `RolledStockStagesTests` pins thickness and width against the model.

The pass count falls out of that same spread. A gap is never one click: the piece is passed, turned over and
passed again, because a single bite does not come out flat and even — so **two passes is the floor**. Beyond
it, **width decides**: a bloom spreads as it thins, overhangs the narrow barrel partway down the schedule, and
from there must be taken in overlapping side-by-side strips at `2 * ceil(width / barrelWidth)`.

So a narrow set gets dearer as the work flattens, which is exactly the argument for the wide set: its barrel
swallows the piece, so every gap stays at the two-pass floor. Grooved rolls sidestep it for the same reason a
real groove does — it constrains the spread — modelled as a barrel the work never outgrows.

`barrelWidth` is a **required** field: without it the mill cannot tell whether stock overhangs, and a silent
default would quietly make every set behave like a wide one.

## 2026-07-26 — Roll-set tooling + mid-pass cooling

`RollSetSpec` is the forming half of the tooling idiom the casting patterns use: the set owns its data, the
mill only reads it, so adding a rolled product is an item def and nothing else. It encodes the design's central
conceit — a heavy manual two-high is not re-gapped mid-schedule, so the barrel carries a **fixed descending gap
sequence** and the player walks the stock along it. The schedule is *geometry, not a setting*: you cannot skip
a step, which is what keeps every pass inside `δ_max` without a runtime check. And because each gap is a real
stopping point, **the product is the thickness you stop at**.

Gaps validated at load (`RollSetValidation`), which matters more than for molds because a bad gap sequence
fails by doing *nothing* when the player feeds stock in.

**Mid-pass cooling** closes the keep-it-hot loop, previously a single check at the bite. The piece sheds heat
whether or not it is moving, so a schedule the line carried at the first gap can drag it down by the last, and
**a jam is self-worsening**. That surfaced a consequence worth pinning: a heavy wheel spins up slower than the
stock cools, so **charge the line before the stock goes in**. An existing test asserted the opposite and was
corrected.

Also fixed a **float→double precision leak** in the def layer (`0.4f` serialises as `0.4000000059604645`, so a
def could never match its golden) — authoring literals are `double`, parsed back as float.

## 2026-07-26 — The mpenergy network's first real consumer: the rolling pass

Until now the whole chain — flywheel, shaft run, bevels, transmissions — was a closed loop that spun to ω_max
and nothing ever spent, because `LoadTorque` returned a hard-coded `0f`. **Nothing in the mod drew a single
N·m.**

`RollingPass` is pure and tested, off three textbook relations: bite `δ_max = μ²R` (hot grips, cold slips, ~30×
the draft hot — that *is* the hot-work-only rule); force `F = Y·w·√(Rδ)`; torque `T = Y·w·R·δ` with **no speed
term**, because plastic deformation resists the same at any ω unlike friction — which is precisely what lets a
pass drag a run to a stall.

Three behaviours fall out with no special-casing, pinned against a real network: **carry or stall, never sag**;
**cold stock is refused at the bite, not stalled**; and **a big flywheel carries a pass that bogs a normal one
down** — the flywheel finally earning its place.

`RollingTorqueScale` (0.02) calibrated against one bridge drive (1 N·m) less friction at ω_max (0.6).
⚠️ The network runs at a **~1 N·m scale** — easy to write out-of-scale test drives and see nothing happen.

Also added the mill's lang keys (en/ru/uk) — the audit found it had none, so it rendered as its raw block code.

## 2026-08-02 - Phase 2 of the layered charge: the column becomes the charge

The blast furnace's charge has always lived in vanilla `BlockEntityCoalPile` block entities sitting in the
shaft. That single fact caused three separate shipped problems, and disassembling `VSSurvivalMod.dll` showed
why: `TriggerPileChanged` and `TryPartialCollapse` are **private**, reached from `OnPlayerInteract` and
`MergeWith` - so they fire on *interaction and merge*, not on neighbour removal. Stripping `UnstableFalling`
from the JSON would never have fixed it. That is why consumption was written top-down ("matching the original
drip order") and why per-layer temperature was scrapped as too complex. One root cause, both symptoms.

Phase 2 replaces the representation without cutting anything over. Each shaft **column** `(x, z)` now owns an
ordered list of segments and the **furnace** owns the columns; `iwex:chargepile` is a near-stateless 16-band
window onto its column. Vanilla's pile machinery is not inherited at all, so `TryPartialCollapse` cannot reach
us - the collapse is not suppressed, it is **absent**.

**`ChargeColumn`** - `ChargeSegment(Material, Units, Temperature, BurdenMix)`, index 0 = the raceway end. Push
at the top, take from the bottom, a partial take splits the boundary segment and **both halves keep the
temperature** (temperature is a property of the material, not the quantity - that is what makes the melt
condition exact at unit granularity rather than per round). `LowestUnits` is the primitive and `Take` is built
on it, so peek and take can never disagree about what a take *would* yield.

**The furnace owns them** behind an opt-in defaulting to off. The hierarchy has a trap: `BlockEntityPuddling-
Furnace` extends `BlockEntityBlastFurnace`, so there is **no class every shaft furnace shares that no
reverberatory hearth inherits**. Enabled at the three leaf shaft classes; the hearths write zero new tree
attributes, proved by a paired set difference rather than a literal key list.

**Re-sequenced at the expansion gate.** The plan had Phase 2 deleting `CoalPileBlastmixPatches.cs`. It cannot:
the furnace still consumes coal piles until Phase 3 rewires it, so deleting the patch takes the shaft walk
with it and turns Phase 1's scenario suite red. Moved to Phase 3 as Task 3.0, fused with the cutover that
makes it safe. ★ The seam already existed - `CollectCharge()` returns `object` and each machine casts, so
blast and cupola can return columns while the hearths keep returning piles.

### Two bugs that would have reached players

⚠ **A save key formatted with `CurrentCulture`.** Under `sv-SE` / `fi-FI` / `lt-LT`, .NET writes a negative
integer with U+2212 MINUS SIGN, not an ASCII hyphen - so `chargeCol_-1_0` is a *different key* per locale.
Measured end to end: save 180 units under `sv-SE`, load under `en-US`, get **60**. Eight of nine columns gone,
only the sign-free `(0,0)` surviving. It would have arrived as an unreproducible save-corruption report from

⚠ **`OnTesselation` enumerating a list another thread refills.** The pile read `ChargeColumn`'s segments live

reads - collision, selection, take, HUD - stay live, because "no cache" is right for those. Headless tests are
single-threaded, which is the only reason nothing caught it.

⚠ The tempting alternative - take the shaft cells out of the layout - would have broken the pile: `FindAnchor-

### Orientation checks generalised - network nodes, stairs, and the coke-oven door

**The gap.** `IsHorizontalSideWord` matched only `north|south|east|west|n|s|e|w`, so every **network node**
orientation was invisible to the oriented-parts check: `ns`, `we`, `ud`, `nswe`, `nsud`, `weud` and the
valves' reversed `sn`/`ew`/`du`. A layout pinning a pipe, passthrough, axle, junction, tuyere or tap axis
would silently not rotate - wrong two times out of four. Latent, not live: every node legend shipped today
is a wildcard or the vertical `-u`.

**The fix.** `ExOrientation` gained `IsOrientationToken` / `RotateOrientationToken` / `RotatesUnderY`.
Letters rotate independently, then the result is put back into canonical axis order (NS, WE, UD) so it lands
on the variant the block actually declares.

* ⚠⚠ **The grammar is exact, not "a run of nsewud letters".** Direction letters spell ordinary words -
  `sun`, `wend`, `used`, `news`, `dune` - and a loose test would orientation-check a MATERIAL segment,
  rotate it, and produce a code matching no block. A token is one direction, or whole axis pairs with each
  axis used at most once.
* ⚠⚠ **Canonicalising loses the valves' direction, and that is a known limit.** `BlockValve` and
  `BlockPressureValve` declare both `ns` and `sn`, where order encodes input -> output; every other node
  treats a pair as undirected and declares only the canonical spelling. The two grammars are
  indistinguishable from the string alone, so this canonicalises - right for pipes, passthroughs, axles,
  junctions, flywheels and mills, wrong for a valve. A layout pinning a directed valve must use
  `LegendAnyFacing`. Pinned by a test so the limit is visible rather than discovered.
* ⓘ A four-way junction (`nswe`) is genuinely rotation-symmetric, so it is invariant and emits nothing.
  Only tokens that actually move are recorded - an entry for `ud` or `up` would buy nothing, since those are
  already required exactly by the code matching literally.

**ALL orientation segments, not the last.** `FindSideSegment` (returning one index) became
`FindOrientationSegments` (returning a list), and `multiblockFacings` became `code -> [indices]`. The old
"the LAST side segment wins" tie-break existed only because a single answer had to be chosen; scanning every
segment removes the tie-break rather than tuning it. ⚠ `RotateSegments` is all-or-nothing: one bad index
discards the whole rotation, because a *partially* rotated code matches no block and would present as
"the structure never completes".

**Coke-oven door: now orientation-checked.** ⚠ My earlier claim that vanilla tracks this door's facing in the
block entity was wrong - it carries a `side` variant and `HorizontalOrientable`, and it was only unchecked
because the layouts wrote `cokeovendoor*`, whose trailing star swallows the SIDE along with the state.
`cokeovendoor-*-{facing}` pins the side and leaves the state wild, which is the only combination that works:
pinning the state would break the structure the moment the player opened the door.

★★ **And the variant is the OPPOSITE of the wall face the door closes** - derived, not guessed:
`liquidBarrierOnSidesByType` gives `cokeovendoor-closed-north` a barrier at face index 2, and
`BlockFacing.ALLFACES` runs N, E, S, W, so a `north` door seals its SOUTH side. ⚠ This is the reverse of our
own convention - `iwex:puddlingchargedoor-south` sits in the south wall, while the coke door beside it in
that same wall must be spelled `north`. `ExCodes.Sealing(wall)` is the only place that inversion is reasoned
about; every layout now names the WALL it fills.

## 2026-08-03 - Orientation schemes analysed; coke oven corrected

### The orientation analysis (docs/design/mechanics/orientation-schemes.md)

Surveyed every `VariantGroup("orientation", ...)` in the suite. It is far more varied than the axis-pair
grammar I built yesterday assumed:

* **Face** `n e s w` (+ `u d` on the pipe outlet) - tuyere, blower, fluid intake, smokestack, canal tap
* **SideWord** `north east south west` - tall hopper, cowper, and vanilla's coke-oven door
* **Axis** `ns we ud` (or just `ns we`) - pipe straight, passthrough, shaft, bevel, flywheel, mills
* **DirectedAxis** `ns we ew sn` - ⚠ the molten canal ENDS, not only the valves
* **Bend** 12 tokens of two ADJACENT faces - `nw se en ws un us uw ue dn ds dw de`
* **Tee** 12 tokens of three faces - `uns uwe dns dwe nes esw swn wne dnu deu dsu dwu`
* **Cross** `nswe nsud weud`

⚠ Bend, Tee and Cross are **not recognised at all** by what I shipped - `nw` and `uns` fail the axis-pair
grammar - so a layout pinning a bend is silently unchecked. Not a regression (nothing was checked before),
but the feature is incomplete and quietly so.

⚠ **Spelling is not canonical and never was.** The bend writes `en` not `ne`, `ws` not `sw`; the tee writes
`uns` in one family and `dnu` in another for the same kind of arrangement. Not mistakes - they came from
whichever rotation was authored first - but they are why a general parser cannot be written.

★★ **One rule covers all seven schemes:** rotate each direction letter preserving ORDER; if the result is a
declared token use it, otherwise use the unique declared token with the same face SET. Verified by hand
across every scheme. The ordered step preserves direction exactly where a scheme declares both spellings;
the set fallback repairs the non-canonical spellings everywhere else. **Neither step alone works** -
ordered-only breaks Axis and Tee, set-only cannot tell `ns` from `sn`.

★ And it needs nothing from a block but **the list of tokens it declares**, which the block already writes.
So the fix is a named registry (`ExOrientations.Axis`, `.PipeBend`, ...) that blocks reference instead of
listing states inline - which also stops the 12 bend tokens being retyped per block, and makes the
`Axis`/`DirectedAxis` ambiguity a build error rather than an unresolvable guess.

⚠ **I was wrong that dropping the valve's flipped variants would resolve the ambiguity** - the molten canal
declares `ew`/`sn` too, and for a canal END that may be genuinely directional rather than cosmetic. The
valve's case is still worth acting on separately: its reversed spellings encode which side the wrench put
the HANDLE on, i.e. appearance masquerading as orientation - and today rotating a structure containing a
valve canonicalises that choice away.

### ⚠⚠ Correction to the orientation analysis: a multiblock must NOT pin a self-orienting node

Checked before recommending any of the registry work, and it inverts the conclusion for network nodes.

**A network node's orientation is not the player's choice.** `BlockNetworkNode.OnNeighbourBlockChange` calls
`RecalculateAndSyncOrientations`, and `BlockMoltenCanal.PickBestOrientation` picks whichever declared token
best matches the connectors around it. The node re-orients itself **whenever a neighbour changes**.

So pinning one in a layout would be actively harmful, in two ways:

1. The structure could **never be completed** - the node picks its orientation from the network, and placing
   it "the other way round" does not stick, so the player has no move.
2. ⚠⚠ A **complete structure could silently come apart**: connect a pipe elsewhere in the world, the node
   re-orients, the cell stops matching - and for a furnace, incomplete means extinguish. The player
   experiences their furnace going out because they plumbed something unrelated nearby.

★ **The dividing line is not "facing vs node token" - it is WHO DECIDES.** Player-fixed orientations (slabs,
stairs, doors, hoppers, cowper intake, cores) are exactly what the oriented-parts feature is for. Network-
decided orientations must never be pinned.

ⓘ The one node code a shipped layout does pin - `lpex:pipe-outlet-fire-u` - is harmless because it is
vertical: no rotation and no recalculation can move it.

★ **What a layout actually wants from a node is a SUBSET test**, not equality: "there is a pipe here that
connects along this axis", where the node's token may contain more faces than required. That composes
correctly with self-orientation - a node re-orienting to serve more connections still satisfies it. Different
feature from oriented parts, same registry underneath, not built, and nothing in the DSL expresses it.

### ★★ The tuyere/outlet case: checking IS needed, and the node does not do it

Refining yesterday's blanket "never pin a network node". The user's actual concern - tuyeres and outlets
must be placed with their pipe connection OUTSIDE the furnace, not inside - is a third case, and it inverts
the answer.

⚠⚠ **The node's own logic does not prevent facing inward.** `BlockNetworkNode.ComputeValidOrientations` marks
a face *forbidden* only when the neighbour is a compatible network block with no connector back. A plain
solid neighbour - refractory brick - falls through to a branch that only ever adds a face as *required*, and
only when the current orientation already points at it. **So nothing stops a tuyere facing into the brick,
and nothing later turns it round.**

★ And unlike a free-run pipe, the required facing here is a property of the **layout geometry**, not the
world: the drawing knows which side of the cell is furnace interior, and that never changes. So the
"a completed structure could come apart" objection does not apply. The residual risk is narrow - a
single-faced node re-picks only on gaining a network neighbour on another face, and every other face of an
embedded tuyere is brick.

So the dividing line is three-way, not two:

| Orientation decided by | Check? |
|---|---|
| Player (placement/wrench) - slabs, doors, hoppers, cores | ✅ what the feature is for |
| Network, free run - pipe straight/bend/junction, canal mid-run | ⛔ never |
| ★ Network, but walled in - tuyere, outlet in a shell | ✅ needed, and nothing else catches it |

★ Preferred expression is "connector faces OUT of the structure" rather than a pinned cardinal - immune to
re-orientation as long as it still faces out, which is the actual requirement. That is the subset test,
narrowed to one face.

## 2026-08-03 - Stage C: block code tables generated from the definitions

`{Mod}Blocks.g.cs` for all five domains, emitted by `test/ExpandedLib.Testing/BlockCodeEmitter.cs`, with a

### ★★ It RUNS the definitions rather than parsing them

A Roslyn source generator was the obvious shape and would have been **wrong**. Codes reach
`ExBlockDef.Create` through helpers - `Core(domain, "puddlingfurnacecore", ...)`,
`Common(domain, "pipes/straight", ...)` - and **the helper adds variant groups the call site never shows**.
A syntactic pass gets the base code and misses the variant grammar, which is the half that matters for
`-{type}-{orientation}`.

`Definitions(domain)` is executable and returns finished `ExBlockDef`s, so executing them yields variant
order and arity exactly as shipped. ⓘ Same trick the goldens already use; exact rather than approximate.

### What an entry looks like

    IwexBlocks.FurnacesTuyere.Any                          // "iwex:tuyere-tuyere-*"
    IwexBlocks.FurnacesTuyere.Orientation.N                // "n"
    IwexBlocks.FurnacesTuyere.WithOrientation("n")         // "iwex:tuyere-tuyere-n"
    LpexBlocks.PipesStraight.WithOrientation("ns")         // "lpex:pipe-straight-ns"

Per def: `Code`, `Any`, a nested constants class per multi-state group, `With{Group}` for each varying
group (pin one, wildcard the rest - what a layout wants far more often than a fully resolved code), and
`Of(...)` when more than one group varies.

★ **Keyed by ASSET PATH, not by code.** Several defs legitimately share one code and differ by a `type`
variant - `pipe` is straight, bend, tjunction, xjunction *and* outlet - so grouping by code would have
merged five incompatible orientation vocabularies into one.

★ **Single-state groups are baked into `Any` rather than wildcarded**: `iwex:tuyere-tuyere-*`, not
`iwex:tuyere-*-*`. A fixed group carries no choice, so a wildcard there only loses precision.

### Notes

* ⚠⚠ The write switch is **`EXLIB_WRITE_BLOCKCODES`, deliberately NOT `EXLIB_WRITE_GOLDENS`**. The latter
  rewrites an entire domain's goldens and has destroyed hand-blessed work before; regenerating a code table
  is a far smaller action and must not be reachable by the same switch.
* ⚠ A generated file with no drift test is worse than no generated file - it looks authoritative and is
  silently wrong the first time a variant group changes. Every suite has one, and the failure message says
  how to regenerate plus the first differing line.
* Entries are sorted, so the file does not churn when a provider is reordered or renamed.
* ⚠ Worldproperty-sourced groups (`loadFromProperties`) carry no states in our definition - the game holds

## Firebox + charge lid — 2026-08-03

Two parts the heating-furnace redraw wanted and neither existed. (The **charge door** did — it only read as
missing because `.Legend('F', IwexBlocks.)` left the file unparseable, which kills completion for the whole
file.)

### What landed

* **`iwex:furnace-firebox-{tier}-{side}`** — block, block entity, and the fuel pool as a **composable
  behaviour** (`BEBehaviorFirebox`). Any refractory tier; the facing is **visual only** (which way the bars
  run), stated in the class doc-comment because a `side` group looks identical to a load-bearing one.
* **`iwex:furnace-chargelid-{side}`** — third def on the `BlockChargeDoor` chassis, no new code.
* **Both branch cutovers.** `CollectCharge`/`ReadChargeMix`/`TryIgniteCharge`/`BurnOutCharge` read beds, not
  vanilla coal piles. `BurnOutCharge` became `protected virtual` on the core to allow it.
* **`c` → `F` on both reverberatory layouts.** `G` (the grating) left with it — the firebars are in the block
  now — and the cell below is air, the ash pit that is deliberately not modelled.

### Why the pool is per-cell state, not shared storage

`firebox.md` asks for "fireboxes that belong to one furnace share one pool, filling costs per cell". What
shipped keeps the **units per cell** and makes the *pool* a distribution rule: `BlockEntityFirebox.Charge`
spreads a deposit over `BlockEntityFurnaceCore.FireboxCells`, and the furnace sums them. Identical arithmetic
and identical feel — one interaction fills the bed, a two-cell reheat firebox costs twice a one-cell puddling
one — but no cell has to own the save and an orphan still holds exactly the fuel it draws. Grouping is by
`CellRole.Firebox`, **never adjacency**: two hearths built back to back would otherwise merge their fuel.

### Two defects the cutover retired

* ⚠⚠ **`@(air|coalpile)` meant an empty firebox satisfied the structure.** Air was an accepted occupant, so a
  reverberatory furnace completed with no fuel cell built at all. A required block cannot.
* ⚠⚠ **The ignition guard was measuring vanilla.** `NoFireboxAsksForMoreThanItsCellsCanHold` bounded the
  threshold at `cells * BlockEntityCoalPile.MaxStackSize` — a hard 16 nobody chose, read off the game at
  runtime, and the whole of B8's first cause. Re-expressed against the firebox's own layer arithmetic
  (6 courses × 2 units = 12/cell). The guard is **kept**, not deleted: its absence let an unreachable
  threshold ship twice. `FireboxMixPerCell`'s default 12 fitting under vanilla's 16 was luck.

### ⚠⚠ And one found while fixing the layout

**`BlockHeatingFurnaceCore` carried the puddling furnace's `Origin(-6,-1)`** while its own core glyph sits at
col 6 / **row 2** — this hearth is a row deeper. Every cell it declared landed one north of the block the
player placed, for the machine's whole life. Nothing could see it: the drawing is internally consistent, so
completion, rotation and the role sets all agreed with each other and the goldens pinned the wrong answer.
Four `FurnaceRoleCellsTests` corner literals were transcribed from it and moved with the fix.

### Tests

exlib 832 ✔ · hpex 52 ✔ · smex 224 ✔ · iwex 1126/1187 · lpex 178/185 — identical on 1.22 / 1.21 / 1.20.

⚠ **All 61 iwex + 7 lpex failures are the cold-furnace and cupola redraw**, not this work: 38→36 chargeable

## 2026-08-03/04 — Orientation work, three real game bugs, and a migration left mid-air

⚠⚠ **STOP: the `side`→letters migration is APPLIED, COMPILES, and leaves 97 tests red.** Decide
finish-vs-revert before anything else. `run-tests.sh 1.21` was **fully green** immediately before it.

### Done and verified green (keep regardless of the migration decision)

* **`ExOrientations`** (exlib) — the 12 declared schemes from `orientation-schemes.md` + the two-step
  rule (rotate letters preserving order → declared? use it → else the unique token with the same face
  set). **18 tests**, including two properties worth keeping: four quarter-turns is the identity for
  every token of every scheme, and every rotation lands on a token the block actually declares — the
  invariant whose absence produced `iwex:crafting-west` and crashed the client.
* **`BlockBehaviorExOrientable`** — `horizontal | omni | network`. `ApplyOrientation(world, pos, token)`
  is the one mechanism both the player path and the network path call. ★ `IsNetworkOriented` is now the
  machine-readable answer to "may a layout pin this?", so `MultiblockLayoutBuilder` can refuse it at
  build time instead of the rule living only in a design doc.
* **The `FromCode` landmines** — `ExOrientation.FacingFromSide()` accepts either spelling and replaces
  `BlockFacing.FromCode(Variant["side"])` at 3 sites. ⚠ `FromCode` returns **null for a letter** and the
  failures were silent: `TryPourMetal` returned 0 forever (*a furnace that fills and never drains, no
  error*), the casting cell collapsed to NORTH, and the tap block dereferenced the null. ★ Already live
  exposure before the rename — network `orientation` groups have always been letters.

### Three real game bugs, two worse than their log lines

* **`game:leather` was never a valid item code.** Vanilla's leather is fully variant-grouped, so a bare
  `leather` resolves to nothing — and with no `*` it is a hard `GetItem`, not a wildcard match. **The
  twin-tub blower had no recipe at all.** Now `game:leather-normal-plain`.
* **lpex passthroughs were not pipes.** The log named the missing block *entity*; the block *class* was
  equally unbound. `ExBlockDef.Class<T>()` keys off the **definition's asset domain**, not the type's
  owning mod, and lpex calls the shared iwex factory with `domain: "lpex"`. Every
  `lpex:pipe-passthrough*` fell back to plain vanilla `Block` — no network node, no `IChimneyVentable`,
  no burst exemption — and **hpex's Lancashire boiler is built from them**. Pinned to `iwex.` literals.
* **hpex was not loading at all.** `<Private>false</Private>` does not propagate to a project's
  transitive closure, so the SDK copied `IronworkingExpanded.dll` in as a second `ModSystem`. ★ The
  control that proves it: exlib is transitive too but absent, because it is declared directly. ⚠ The
  release zip would have shipped the same way.

* `HopperTallPileCap` 128 → **16**: a shaft cell is a vanilla `game:coalpile` whose `MaxStackSize` is a

### ⛔ Dead ends — do not re-try (all measured)
